# 01 — Product requirements and scope

> Source: `01_SupportPilot_Product_Requirements.docx` (SP-PRD-001 v1.0, 2026-09-07)

## 1. Product definition

SupportPilot is a multi-tenant AI support agent built on Onyx. It helps authorized support staff find
customer, order, shipment, and ticket information; summarize support history; and request controlled
business actions. It uses real services, a persistent PostgreSQL database, individual user
identities, policy-based authorization, approval workflows, and audit records.

**Core rule:** the model may propose tool use, but trusted services decide what is allowed and
perform every real action.

### Goals

- Reduce the time required to find and explain support information.
- Preserve the permissions of the authenticated user on every request.
- Allow useful automation without giving the model unrestricted database or system access.
- Require independent approval for financial, administrative, destructive, or externally visible actions.
- Create evidence that explains who requested, approved, and executed each sensitive action.

### Non-goals (first release)

Autonomous refunds without approval · free-form SQL generated by the model · general shell,
file-system, or cloud-administration access · training or fine-tuning a foundation model · replacing
the existing support system of record before integrations are proven.

## 2. Users and roles

A person may hold more than one role, but sensitive approvals must still satisfy separation of duty:
the requester cannot approve the same high-impact action when policy requires an independent approver.

| Role | Purpose | Typical permissions |
|---|---|---|
| Support Agent | Handles normal customer questions | Read assigned customer and order data; create notes; propose limited actions |
| Support Manager | Supervises support work | Read team records; approve selected actions within policy limits |
| Finance Approver | Reviews financial actions | Approve or reject refund requests within assigned limits |
| Auditor | Reviews evidence | Read audit records and action history; no business-data changes |
| Product Administrator | Manages agents and tool registration | Control-plane access; no automatic business-data access |
| Platform Administrator | Operates infrastructure | Deployment and emergency administration through separate accounts |

## 3. Scope

### Business objects

Organizations and memberships · customers and contact details · orders and order items · shipments
and status · tickets and ticket messages · internal notes · refund requests, approval decisions,
action jobs, execution results · audit events and idempotency records.

### Tool scope

| Tool | Type | Behavior |
|---|---|---|
| `search_customers` | Read | Find customers visible to the authenticated user |
| `get_customer` | Read | Return an approved subset of one customer record |
| `get_order` | Read | Return order, item, and shipment status for an authorized order |
| `get_ticket` | Read | Return a ticket and permitted conversation history |
| `add_internal_note` | Write | Add an internal note after authorization and input checks |
| `propose_refund` | Proposal | Create a pending refund request; **does not move money** |
| `get_action_status` | Read | Return the status of a previously requested action |

Full schemas: [../specs/api-contract.md](../specs/api-contract.md).

## 4. Core user journeys

### Read an order

1. The user signs in through Keycloak and opens the SupportPilot agent in Onyx.
2. The user asks for order `ORD-2001`.
3. The model requests the `get_order` tool with the order number.
4. Onyx sends the tool request **and the user access token** to the SupportPilot API.
5. The API validates identity, obtains trusted resource attributes, and asks OPA for a decision.
6. The API performs a parameterized query under the restricted API database role.
7. PostgreSQL row security limits returned rows to the organization in the trusted request context.
8. The API returns a minimal result to Onyx, and the model writes the final answer.

### Request a refund

1. The user asks for a refund and provides order, amount, currency, and reason.
2. The model requests `propose_refund`. **The model does not call a payment provider.**
3. The API validates order, amount, currency, reason, user permission, and tenant ownership.
4. The API creates an immutable action request with a hash of the exact approved payload.
5. An authorized **independent** approver reviews and approves or rejects.
6. The worker claims the approved job and executes it **once** through an allowlisted adapter.
7. The worker stores the provider reference, outcome, timestamps, and audit records.
8. The user checks the action status and receives the confirmed outcome.

## 5. Functional requirements

| ID | Requirement | Acceptance signal |
|---|---|---|
| FR-01 | Every chat user authenticates through the configured identity provider | Requests without a valid token are rejected |
| FR-02 | Onyx forwards the user identity to SupportPilot actions | The API receives and verifies a user-bound token |
| FR-03 | The model can call only explicitly registered tools | No generic SQL, shell, HTTP, or file tool is available |
| FR-04 | Read tools return only authorized records and approved fields | Cross-organization and excessive-field tests fail safely |
| FR-05 | Sensitive writes use proposal, approval, and worker execution | The API cannot directly execute the protected effect |
| FR-06 | Every tool request has a correlation identifier | Logs can reconstruct one request across services |
| FR-07 | Repeated action submissions do not cause repeated effects | The same idempotency key produces one execution |
| FR-08 | Users can inspect the status of their action requests | Pending, approved, rejected, executing, succeeded, failed states are visible |

## 6. Security and quality requirements

- Authorization is performed by trusted code for every tool call, **including calls generated after
  reading untrusted content**.
- The model never receives database passwords, service secrets, approval credentials, or unrestricted
  access tokens.
- User identifiers, organization identifiers, roles, and approval status are **not trusted** when
  supplied as model arguments.
- Runtime database roles do not own protected tables and have no superuser or row-security bypass
  privileges.
- External text is data. It cannot register tools, change policies, grant permissions, or modify
  system prompts.
- Tool parameters use strict schemas, length limits, type checks, enumerations, and business constraints.
- Agent loops have limits for model calls, tool calls, elapsed time, tokens, and cost.
- Sensitive output is minimized and redacted before it enters model context or logs.
- The system denies access when Keycloak, OPA, or required authorization data is unavailable.

## 7. Product rules

| Rule | Required behavior |
|---|---|
| Identity authority | Only the verified access token and server-side records define the current user and organization |
| Tenant isolation | Every protected business object belongs to an organization and is checked at API **and** database layers |
| Least privilege | Each service, database role, tool, and user receives only the permissions required for its task |
| High-impact actions | The exact payload must be approved independently before execution |
| No model authority | Model text, reasoning, confidence, or tool arguments never grant permission |
| Evidence | Authorization decisions and sensitive state changes create tamper-evident audit events |

## 8. Success criteria

- [ ] Alice can read an order in Cedar when her membership permits it.
- [ ] Alice cannot read another organization's order by changing the order identifier.
- [ ] A prompt claiming administrator status does not change authorization.
- [ ] A malicious instruction stored in a ticket cannot add tools or change policy.
- [ ] A refund cannot execute before the required approval exists.
- [ ] The requester cannot approve their own refund when independent approval is required.
- [ ] Retrying an approved action does not execute the effect twice.
- [ ] The audit trail identifies requester, approver, policy version, payload hash, executor, outcome.

## 10. Glossary

**Agent loop** — the repeated cycle of model decision, tool request, tool result, next decision.
**Control plane** — administration of agents, prompts, tools, policies, deployments, credentials.
**Data plane** — user requests, model calls, tool calls, database access, action execution.
**OPA** — Open Policy Agent, the service that evaluates policy and returns a decision.
**RLS** — row-level security in PostgreSQL.
**Tool** — a narrow operation the model may request through a defined schema.
**Worker** — a service that executes approved jobs outside the chat request.
